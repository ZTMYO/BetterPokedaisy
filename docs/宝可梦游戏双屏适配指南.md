# 宝可梦游戏 AYN Thor 双屏适配指南

> 目标：在 AYN Thor（双屏 Android 掌机）上让更多单屏宝可梦游戏实现"上屏游戏 + 下屏伴侣"双屏游玩。
> 依据：仓库 main 分支源码与 `docs/DEVELOPMENT.md`、`gamedata/README.md` 的官方工作流。

## 〇、先建立正确的认知（这决定了你要做多少工作）

**"双屏游玩"和"伴侣适配"是两件事：**

1. **双屏游玩本身零适配**。`DualScreenPresentation.kt` 会自动把游戏画面放主屏、把伴侣 UI 放到第一个副屏（Thor 的 Screen-2，1240×1080）。任何 GBA/GBC/GB ROM 都能上双屏跑起来——模拟核心是 mGBA，游戏能不能"被读懂"才是适配的对象。
2. **适配 = 让伴侣能读取这款游戏**。识别链路是：`Poller.detect()` 读 ROM 头（游戏代码 + 修订字节 + 整文件 SHA-1）→ 匹配到某个 `GameKind` + `NativeConfig`（内存地址表）→ `ActiveTables.kt` 选择物种/道具/地图名称表 → 各标签页实时解码内存绘制。

所以你的实际任务是：**为一款新游戏补齐 ①识别 hash → ②NativeConfig 地址 → ③名称/数据表 → ④回归测试** 这条链。

## 一、先判断你的游戏落在哪条路径

把 ROM 放进 `files/roms/` 直接玩，按 app 的表现对号入座：

### 路径 A：已被官方支持
README 的支持列表（红/蓝/黄、金/银/水晶、火红/叶绿、绿宝石、红/蓝宝石、白金/心金/魂银、黑 + 40 余个 hack）里有它 → 什么都不用做。版本号必须精确对应，hack 按文件 hash 识别。

### 路径 B：BEST EFFORT 自动兜底（先试试这个，零开发）
未识别 hash 的 ROM 不会直接报死。`BestEffort.kt` 会用**同引擎所有已知 config** 去试读运行中的游戏：

- 试读队伍（校验和解密是否通过）、比对 ROM 里的名称表、检查图标表；
- 全部吻合 → 自动直接用（SURE）；
- 部分吻合 → 伴侣弹出候选列表让你手选，选完按 SHA-1 记住，下次自动用；
- 不吻合的部分（如图标表对不上）会自动降级关闭，不会出现错误精灵图。

很多 hack 保留了零售版 RAM 布局（Orange Islands 在早期就是被当 FireRed 读出来的），**路径 B 可能已经够玩**。你只需在 app 里确认一次。

### 路径 C：完整适配（本指南的主体）
路径 B 读不了、或读出来缺标签页/图标/名称时，按下面流程做正式适配。

## 二、适配难度分级（选游戏前先看这个）

按引擎/修改方式，工作量从低到高：

| 级别 | 类型 | 典型代表 | 为什么 |
|---|---|---|---|
| ★ | FireRed/零售版**就地修改**的 hack（16/32MB，保留 rev0 代码与 RAM） | Orange Islands、Ultra Violet、Rocket Edition、Ash Gray、Ghost Grey | RAM 地址零改动，`base = 'firered_rev0'` 直接继承；只需 ROM 侧的名称表 diff 和 hash 注册 |
| ★★ | **CFRU** hack（FireRed 基座，32MB） | Unbound、Radical Red、Sword/Shield UP、GS Chronicles | RAM 大多保留 rev0 布局；需处理重编号的物种表、自己的图标表（用 literal-pool 技术找） |
| ★★ | pokeemerald 零售版就地修改 | Glazed、Emerald Legacy | 零售 Emerald 的 RAM/代码 + 自己的表 |
| ★★★ | **pokeemerald-expansion** 系 hack（"PRET x RHH" 开屏） | Heart and Soul、SoulGold、TMT2、Imperium、Wishes、Dreamstone | BoxPokemon 位打包（`speciesMask`/`moveMask`/`ppMask`）、smol 压缩图标、BattlePokemon/SaveBlock 布局随版本变化 |
| ★★★★ | **现代 gcc 全量重建**（无任何零售地址） | Recharged Yellow/Emerald、Quetzal、Elite Redux | 所有地址都要重新找；有 GF ROM header（0x08000100）的还算有线索 |
| ★（另一体系） | **GB/GBC（Gen 1/2）** | 初代红蓝黄、金银水晶及 Polished Crystal、Prism 等 | 独立的 `Gen1Reader`/`Gen2Reader`，地址来自 pret 反编译工程的 .sym 文件，有源码的 hack 反而容易 |

## 三、完整适配流程（Gen 3 为例）

### 第 0 步：准备环境

- **Docker**（必需）：无头采集镜像 `native-capture/Dockerfile`（libmgba + aarch64 gcc）。
- **Git Bash / Linux 环境**：所有脚本都是 bash + python3。Windows 上建议 WSL2 或 Git Bash + Docker Desktop。
- **注册你的 ROM 和存档**：编辑（未跟踪的本地文件）`scripts/host_roms.conf`，每行 `key|标签|ROM路径|存档路径`（存档可省略=全新游戏采集）。key 将与测试夹具目录同名。
- 若涉及反编译工程路径（GB/GBC 或表生成），复制 `local.mk.example` 为 `local.mk` 填 `DECOMPS`。

### 第 1 步：采集内存夹具（两种途径，任选）

**途径 1：无头采集（推荐，不需要 Thor）**

```bash
make capture-image                                          # 首次构建 Docker 镜像
scripts/capture_fixture_headless.sh <key>                   # 默认引导脚本自动跳过开场/标题
# expansion 系 hack 用专用引导：
scripts/capture_fixture_headless.sh <key> --script native-capture/boot/rhh_splash.txt
```

产物：`app/src/test/resources/fixtures/<key>/{ewram.bin,iwram.bin,README.txt}`（256KB EWRAM + 32KB IWRAM 快照）。`mgba_dump.c` 还能驱动脚本化战斗（`setwildbattle` 等指令）采 battle 夹具——BATTLE 标签页必须有 battle 夹具才能验证。

**途径 2：真机采集（Thor 在场时）**

```bash
scripts/capture_fixture.sh <key>     # 通过 adb 触发 app 的 EXTRA_DUMP_FIXTURE 转储
```

### 第 2 步：找内存地址（最核心、最耗时）

原则（`docs/DEVELOPMENT.md` "How a new ROM gets supported" 全文必读）：

1. **先找 `gPlayerParty`**：对 EWRAM 做 4 字节对齐扫描，找能通过 Gen3 `struct Pokemon` 校验的候选（PID^OTID 密钥、PID%24 子结构顺序、解密后 12 个 word 的 16 位校验和）。校验和命中约 1/65536 概率，信号强但**不是证明**。
2. **跨会话验证稳定性（铁律）**：任何地址必须在 **3 次以上独立采集**中逐字节一致才可信。教训：Emerald Rogue 的候选地址连续两次采集都"稳定"还有 IWRAM 指针佐证，第三次采集暴露了它是可重定位的临时缓冲区。**单次/双次采集确认的地址禁止入库。**
3. **其余 RAM 字段**（saveBlock 指针、背包口袋、加密密钥、gMain、mapHeader、objectEvents）用指针链/已知值反查，不要假设零售版结构偏移仍然成立。
4. **ROM 侧表**（图标图形的 tiles/palette 表、名称表）是另一场狩猎：
   - 名称表最好找：锚定 1-2 个已知名称（如 "Bulbasaur"@1）按定长步长走表；注意一张表可能分裂（Amethyst 教训：锚 "Bulbasaur" 走出的表在 251 之后混进了招式名表，真正的全量表在别处）。
   - 图标表最难：找仍然字节相同的辅助函数（`GetMonIconTiles`/`GetItemIconGfxPtr`），它的 literal pool 里必有重定位后的表地址（Gaia/Amethyst 技术）；必要时用项目 Docker 镜像构建**未打补丁的**钉住版 pokefirered，从 `nm` 符号表拿函数地址。
   - **任何候选地址都要端到端解码出图看一眼**（渲染成 PNG 确认是认得出来的精灵/道具），不能只凭"像个合法 ROM 指针"就采信。
5. **expansion 系注意**：校验和扫描前先做 `speciesMask`（如 0x7FF）等掩码，否则 packed 字段过滤不出合法物种；`BattlePokemon` 大小、SaveBlock1 布局随 expansion 版本变化，只有 battle 采集能确认；道具图标可能是 smol 压缩（`Smol.kt` 处理）。

### 第 3 步：写 gamedata 配置

新建 `gamedata/gen3/hacks/<game>.toml`（格式见 `gamedata/README.md`，每个字段语义见 `gamedata/schema/gen3_config.toml`）：

```toml
[config.myhack]
base = 'firered_rev0'        # 或 'firered_rev1' / 'emerald' / 另一个 hack config
# 只写与 base 不同的字段，例如：
monIconTable = 0x09C018FC    # ROM 图标表（literal-pool 技术找到）
itemDescs = { preset = 'vanilla', base = 0x0872DB0C }
enemyParty = 0x0202402C      # BATTLE 标签页：敌方队伍
battlerPartyIndexes = 0x02023BCE
battleStructPtr = 0x02023FE8
monToSwitchIntoOff = 0x5C
actionCursor = 0x02023FF8    # 触屏战斗控制
moveCursor = 0x02023FFC
pokedex = 'POKEDEX_MYHACK'   # DEX 标签页（引用 records）
guideTables = 'GUIDE_TABLES_MYHACK'  # GUIDE 标签页
```

`base` 继承机制让 ★/★★ 级游戏通常只需十几行。**注释里必须写清每个地址是怎么找到的**（仓库所有 config 都是如此，这是传统也是审查依据）。

### 第 4 步：生成数据表（名称/属性/招式等）

按基座选生成器，为 ROM 生成专属表（输出到 `companion/data/*Gen.kt`）：

| 基座 | 生成器 | 已有范例 |
|---|---|---|
| CFRU hack | `scripts/gen_cfru_tables.py <key>` | Radical Red、GS Chronicles |
| pokeemerald-expansion | `scripts/gen_expansion_tables.py <key>`（需先在 `GAMES` 加条目） | SoulGold、Wishes、Dreamstone |
| FireRed 就地修改 | `scripts/gen_firered_hack_tables.py <key>` | Ghost Grey、Rocket Edition |
| Emerald 就地修改 | `scripts/gen_glazed_tables.py` 等 | Glazed |
| 全量重建 | 专用脚本（`gen_recharged_yellow_tables.py`、`gen_quetzal_tables.py`…） | Quetzal 系列 |
| Gen 1 / Gen 2 | `gen_gen1_tables.py` / `gen_gen2_tables.py`（地址来自 pret decomps 的 .sym，需 `DECOMPS`） | Prism、Polished Crystal |

### 第 5 步：接入识别与表选择

1. **SHA-1 常量 + detect 分支**：在 `Poller.kt` 加 `MYHACK_V1_0_SHA1` 常量，在 `detect()` 的 hash `when` 分支里映射 `kind = GameKind.MYHACK; nativeCfg = NATIVE_MYHACK`。
2. **GameKind 枚举**：新增种类（若作为现有游戏的变体运行——如某些 hack 以 `GameKind.FIRERED` + `ActiveTables.fireRedHack` 的 `HackText` 叠加运行——则可省去）。
3. **ActiveTables.kt**：把生成的名称表挂到该 `GameKind` 的表选择逻辑上。

### 第 6 步：生成与测试

```bash
make gamedata            # TOML -> NativeConfigsGen.kt / GameDataRecordsGen.kt / pd_configs_gen.h
make test                # JVM 单测
```

**必须新增** `app/src/test/kotlin/.../companion/data/MyhackDecodeTest.kt`：用第 1 步的夹具解码，断言已知真实值（队伍里实际的宝可梦/等级/HP、背包里实际的道具）。这是防止未来重构把你辛苦找到的地址改坏的保险，也是官方合并的硬性要求。仓库现有 273 个夹具、每款支持游戏一个 DecodeTest。

### 第 7 步：真机验证

```bash
make install             # 构建并装到 Thor（adb）
```

逐项核对：PARTY / BAG / BATTLE（进入战斗看下屏是否自动切换）/ MAP / DEX / GUIDE；确认无误后 `make check` 全量检查。

## 四、Gen 1/Gen 2（GB/GBC）补充

- 读内存的是独立的 `Gen1Reader.kt` / `Gen2Reader.kt`（大端、不同结构），配置常量在 Kotlin 内（如 `GEN2_PRISM`），不走 `gamedata/` TOML。
- 零售游戏地址直接来自 pret 反编译工程构建的 `.sym`（`DECOMPS` 指向本地克隆）。
- **有源码的开源 hack 最容易适配**：自己 `make` 出字节一致的 ROM + 拿符号表，如 PureRed/PureBlue、Polished Crystal；无源码的（Crystal Clear、Prism）则靠 ROM 内容比对。
- Gen 2 的地图/图鉴/图标走 `Gen2Art`/`Gen2Dex`，从 ROM 直接重建。

## 五、务实建议

1. **从路径 B 开始**：先把目标 ROM 丢进 app 看 BEST EFFORT 能读到什么，很多情况下已经"能玩"，缺的只是图标或 DEX。
2. **选游戏看基座**：优先选"FireRed 就地修改"类（★级），一天能搞定；expansion 系预留一周；全量重建先确认 GF ROM header 是否在场。
3. **Windows 工作流**：采集/生成全部可在 Docker + Git Bash 完成；真机验证用 adb（Thor 连 USB 开调试）。
4. **不要手改生成文件**：`NativeConfigsGen.kt` 等只能由 `make gamedata` 生成。
5. **尊重铁律**：地址 ≥3 次独立采集验证；ROM 表端到端解码确认；每个地址注明出处。
6. **上游贡献**：做完的游戏可以提交到官方仓库的 Game requests 讨论区，作者维护活跃（当前 1.3.3 版）。

# 方案 B 执行计划：中文 ROM 适配（以漆黑的魅影 5.0EX+ 为试点）

## 阶段 0：环境与 ROM 准备（前置）

**本机工具链实测（2026-10-31）**：
| 工具 | 状态 | 用途 |
|---|---|---|
| Python 3.12 | ✅ | 扫描/生成脚本 |
| Docker | ❌ 缺失 | 无头采集镜像（native-capture）必需 |
| JDK | ❌ 缺失 | Gradle 构建 APK 必需（JDK 17） |
| adb | 待确认 | 真机采集与安装 |
| Android SDK + NDK | ❌ 缺失 | assembleDebug 必需（CMake 交叉编译 mGBA/melonDS） |

补装方案：Docker Desktop（WSL2 后端）+ JDK 17 + Android Studio（自带 SDK/NDK）+ platform-tools。
替代：APK 构建可走 GitHub Actions（fork 仓库推分支，CI 出包），本机只跑 Python 分析和夹具采集（采集又依赖 Docker，故 Docker 基本绕不开）。

**需要用户提供的文件**（放入工作区）：
1. 漆黑的魅影 5.0EX+ ROM（.gba）——hack 免费分发，但请确保来源可靠
2. 一个中后期 .sav 存档（有 3-6 只宝可梦、背包有道具）——用于内存采集
3. 在 `scripts/host_roms.conf` 注册：`ebonyphantom|漆黑的魅影 5.0EX+|<rom 路径>|<save 路径>`

## 阶段 1：ROM 摸底（拿到 ROM 后立即执行，纯 Python 分析）

- 读 ROM 头：游戏代码（汉化绿宝石常为 BPEE 或自定义）、容量、修订字节
- 整文件 SHA-1（后续 detect() 注册用）
- 与零售绿宝石（美/日）分块 diff：确认就地修改范围、代码区改动比例 → 决定 base config 选谁
- 字库侦察：定位中文点阵字形数据（1bpp/2bpp），确定双字节编码方案（区码+位码），为解码器准备

**关键预期**：漆黑底本是"漫游&TGB 联合汉化绿宝石"，其 RAM 全局地址与美日零售是否一致必须实测，不能假设。

## 阶段 2：内存采集与地址确认

```bash
make capture-image
scripts/capture_fixture_headless.sh ebonyphantom
```
- 校验和扫描找 gPlayerParty → **≥3 次独立采集验证稳定性**（铁律）
- 指针链确认 SaveBlock1/2、gBagPockets、加密密钥、gMain、mapHeader
- 战斗采集：mgba_dump 脚本化 setwildbattle 抓 battle 夹具
- 对比 NATIVE_EMERALD：若全部一致，config 只需十几行差异

## 阶段 3：中文化基础设施（与具体 ROM 解耦，可并行开工）

1. **中文字体**：选缝合像素字体（Fusion Pixel Font，OFL 许可）→ 参照 `scripts/gen_jp_font.py` 写 `gen_zh_font.py` → 接入 `PixelTypeface`/`BitmapTtf`
2. **UI 汉化**：`AppLanguage` 加 `ZH("ZH", null, "zh", "中文")`；`TrCore/TrCompanion/TrSettings/TrLibrary/TrCompanionInfo` 全部词条补 `zh = ...` 字段；`check_translations.py` 卡完整性
3. **CJK 文本解码器**：`GameText` 加中文实现（用阶段 1 提取的码表），解码中文 ROM 的名称表
4. **BestEffort 适配**：名称比对环节对 CJK 编码的 ROM 跳过（拉丁字符表必然不匹配），降级为"队伍可读 + 玩家手选确认"

## 阶段 4：数据表与配置接入

- `scripts/gen_ebonyphantom_tables.py`：从 ROM 提取中文物种/道具/招式/地名表（解码器 + 锚点搜索）
- `gamedata/gen3/hacks/ebonyphantom.toml`：`base = 'emerald'`（预计）+ 差异字段 + 出处注释
- `Poller.kt`：SHA-1 常量 + `detect()` 分支；`ActiveTables.kt` 挂中文表
- `make gamedata` 生成配置代码

## 阶段 5：测试与真机验证

- `app/src/test/.../EbonyPhantomDecodeTest.kt`：夹具断言真实值
- `make check` 全量 → `make install` 上 Thor 逐项核对 PARTY/BAG/BATTLE/MAP/DEX

## 主要风险

1. **底本不确定**：汉化绿宝石的 RAM 布局若与零售不同，阶段 2 工作量升一级
2. **中文显示宽度**：像素字体下中文名 2-4 字 ≈ 8-16 个拉丁字符宽，PARTY/BAG 列表布局需适配
3. **版本碎片化**：漆黑有 5.0 / 5.0ex / 5.0EX+ / BW版 / DP版 及 2026 年新版 v6.7.0，每个变体 hash 不同、表可能有差异，首个试点锁定 5.0EX+ 一个版本
4. **上游合并**：中文支持属新体系（字体许可、解码器、CJK 适配），作为 fork 自用先行，上游视情况再谈

## 执行顺序（修订：汉化补丁版优先）

**先做四款已支持游戏的汉化补丁版**（激进红 4.1 / 无界 2.1.1.1 / 格查尔 Alpha 9 v0 / 西火箭队 1.5），理由：

1. **RAM 直接继承英文版配置**——汉化补丁只改文本/图，不动代码和内存布局（先例：无界法语版 `NATIVE_UNBOUND_FR` "English's RAM, every literal pool unchanged"）。最难、风险最高的"找地址"环节变成一次采集验证即可。
2. **上屏游戏画面也是中文**，完整中文体验，正中目标。
3. **新建基础设施完全同款**：中文字体 + ZH UI + CJK 解码器做一次，四款复用。

每款汉化补丁的增量工作：
- 采集 1-2 次内存，用英文版 config 验证队伍能解码（证明 RAM 未变）→ 成为该补丁版 DecodeTest 的夹具
- 提取该补丁的中文字符集（各汉化组字库/编码不同，需逐补丁提取）
- 用解码器从补丁 ROM 生成中文名称表（物种/道具/招式/地名）
- `Poller.kt` 注册补丁版 SHA-1 → 指向英文版 config + 中文 GameText 变体
- 注意：补丁必须基于对应精确版本（激进红汉化须基于 4.1、无界基于 2.1.1.1），且确认补丁是纯翻译（不含改版改动），否则 RAM 验证会暴露

**之后再做中文原生改版**：漆黑的魅影 5.0EX+ → 永恒之焱 → 究极绿宝石 v5.x（这些底本不是官方英文零售版，地址要完整实测）。

### 关键方法论修订
"英文版存档跨 ROM 加载"验证法在本机不可行（英文 ROM/存档均在旧机器）。
纯翻译判定的强证据 = **ROM 表静态校验**：翻译补丁只改文本/图，若英文版配置记录的
ROM 表地址在汉化 ROM 中端到端可解析（ID 连续、指针落在 ROM 内），则代码与 RAM
布局未被移动，英文版 NativeConfig 可直接继承。 precedents：unbound_fr。
